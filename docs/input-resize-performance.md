# 连续鼠标移动与窗口缩放：修复与验证

## 场景与指标

本次针对 Windows x64 下的 Jalium.UI 真实窗口，初始外框 800×600、完整默认主题、默认自绘标题栏和 Auto 后端。空窗口使用 Software，添加应用内容仍进入完整渲染路径。

测试分别记录进程 CPU 时间、工作集、私有提交量、线程和句柄，以及已有 HoverTrace 的消息、调度、整树绘制和实际呈现计数。CPU 百分比按一个逻辑核心计算；不能直接与任务管理器按整台机器归一化的百分比混用。

固定轨迹使用 `SetCursorPos` 产生真实鼠标输入，先把本次创建的窗口放到工作区内相同位置；只在目标窗口保持前台时移动光标。每段发送 240 个输入点，设置最多每秒 60 个。原生尺寸变化由 `SetWindowPos` 产生，前后用进入／退出缩放消息覆盖 live-resize 路径。因此该轨迹能复现处理成本，但不是物理边框拖拽本身。原始输出保留实际操作数与耗时，不把请求频率冒充实际频率。

关闭日志的配对用于进程资源比较；另一次开启追踪和被动 GC 诊断的配对用于调用次数分析。每次都启动新进程，操作后保留 10 秒静置，检查最终尺寸、响应和正常关闭。不强制 GC，不裁剪工作集。

## 已修复的根因

### 主帧缓冲与图层暂存的重复分配

旧 Software `Resize` 对每个新尺寸分配并初始化整块缓冲区，再复制保留前缀。现在容量足够时原地调整逻辑长度，只清零新增尾部；需要增长时先分配候选缓冲区，成功后再提交，保留原有线性字节前缀和失败回滚。

增长容量有上界，额外余量最多 16 MiB。实际拥有字节数仍按真实容量报告。空闲压缩释放多余容量，不把逻辑尺寸减小算成物理释放。

小 retained layer 的整窗隔离缓冲按嵌套深度复用，最多缓存四层、总容量不超过 32 MiB，并纳入原有 retained 预算。重新使用前清空逻辑像素；空闲回收和销毁释放缓存。超出限制的临时缓冲不常驻。

### 已有像素被再次完整绘制

时序记录复现了“新尺寸完整画面已呈现，随后又收到系统绘制请求”。旧路径又清空目标、重画整棵视觉树。

现在成功完成当前尺寸的完整 Software 帧后，只在没有更新失效、尺寸仍匹配时确认已覆盖的原生绘制区域。后续空区域绘制请求不再制造新的完整失效。

系统若仍要求非空区域重绘，只有自动空窗、像素有效、尺寸一致、没有待处理布局或脏内容时，才重新提交现有 CPU 像素。此过程仍是真实呈现，继续计入 FrameHistory 和呈现次数，但不重新测量、清空或重画视觉树。内容变化、自定义绘制、GPU 目标、失败帧和未完成的尺寸变化继续走原路径。

### 每次移动都重复注册离开监听

client 与 nonclient 分别记录已成功注册的鼠标离开监听及对应 HWND。移动期间复用已有注册；失败会重试，离开、失去捕获、停用、销毁或 HWND 改变时重新建立所需状态。

没有节流或丢弃公开的 PreviewMouseMove、MouseMove、PointerMove。专项测试断言每个输入都到达，且最后位置保持正确。尺寸合并继续使用框架已有的 CompositionTarget 帧时钟，结束缩放时保留最终尺寸。

### 有待绘制工作时的压缩／恢复往返

空闲压缩检查实际脏内容、待布局和待尺寸，而非仅检查调度标志。有待处理工作时不先压缩，避免下一帧立刻重新扩展。已经由同步呈现完成的调度唤醒不会阻止真正空闲时的回收。

## 配对实测

以下为同位置、同输入点、关闭追踪和被动 GC 日志的 NativeAOT 配对。CPU 是整段进程 CPU 时间；数值受操作系统调度和 CPU 时间量化影响，不是所有机器上的性能保证。

| 阶段 | 输入数／版 | 旧版 CPU ms | 修复版 CPU ms |
| --- | ---: | ---: | ---: |
| 空白区域移动 | 240 | 62.500 | 15.625 |
| 标题栏悬停移动 | 240 | 93.750 | 46.875 |
| 第一轮连续缩放 | 240 | 437.500 | 375.000 |
| 第二轮连续缩放 | 240 | 562.500 | 468.750 |

两段缩放合计从 1000 ms 降到 843.75 ms，减少 15.6%。另一组开启追踪的同轨迹配对从 1421.875 ms 降到 937.5 ms。标题栏悬停在追踪组反而从 109.375 ms 增至 140.625 ms，因此不能宣称其 CPU 有稳定的百分比降幅。

追踪组整个流程的整树绘制为 **850 → 492**；实际呈现为 **890 → 889**。这一区别是有意的：减少重复绘制，不隐藏系统要求的像素提交。被动观察到的托管分配增量为 4,983,368 → 4,632,256 bytes；该值包含诊断开销。采样到的调度队列深度最大为旧版 0、新版 1，没有观察到持续堆积。

内存并非所有指标都下降。关闭追踪的配对中，整个流程工作集峰值为 **27.887 → 28.219 MiB**，私有提交峰值为 **13.680 → 14.738 MiB**；静置结束的私有提交为 **11.188 → 11.523 MiB**。预留容量减少分配次数，但会暂时保留更多容量，不能把它包装成峰值内存下降。该测试也不构成单空窗低于 20 MB 的验收。

### 更长的操作与真实边框拖拽

修复版另执行 2000 个鼠标移动点和 2000 个尺寸变化点，总历时约 115 秒。窗口最终外框回到 800×600，响应检查零失败。工作集峰值 30.383 MiB，私有提交峰值 16.949 MiB，静置结束私有提交 13.621 MiB；末尾 10 秒没有采到新增进程 CPU 时间。这是有限时长观测，不是永久无泄漏证明。

新增 `measure-window-drag-stress.ps1` 进一步覆盖普通连续移动、快速往返、真实上边框持续拖拽，以及每三秒交替移鼠标／拖边框。各活动阶段持续 15 秒，前后各静置 10 秒。驱动通过实际 HTTOP 命中与 SendInput 按下鼠标，使用系统原生模态缩放循环；阶段内不通过 SetWindowPos 改变尺寸。高精度等待计时器只存在于外部输入驱动中，创建和关闭成对管理，未改变应用计时器配置。

| 真实 OS 输入场景 | 旧版输入数 | 新版输入数 | 旧版／新版实际频率 次/秒 | 旧版／新版单核 CPU % |
| --- | ---: | ---: | ---: | ---: |
| 普通连续移动 | 900 | 900 | 60.00 / 59.97 | 2.40 / 2.50 |
| 快速往返 | 3485 | 3485 | 232.33 / 232.31 | 6.25 / 5.00 |
| 持续拖上边框 | 1709 | 1849 | 112.71 / 122.01 | 24.53 / 26.81 |
| 移动／拖边框交替 | 1810 | 1820 | 120.64 / 121.30 | 13.12 / 10.41 |

两版所有阶段都正常结束、边界准确恢复，响应失败为 0，采样到的调度队列深度最大均为 1。新版纯拖边框的总 CPU 增加，其处理输入也增加；每次输入 CPU 为旧版 2.1760 ms、新版 2.1971 ms，基本持平，不能宣称这个场景也实现了 CPU 降幅。快速往返不会额外触发整树绘制；实际尺寸变化仍需要绘制。

高频整组工作集峰值为 **33.461 → 35.863 MiB**，私有提交峰值为 **18.406 → 20.781 MiB**，静置结束私有提交为 **14.754 → 17.645 MiB**。这组再次说明本轮减少的是重复分配和重复绘制，并非所有工作集、私有提交或 CPU 数值都下降。没有观察到队列持续积压或静置时持续重画，但预留容量和运行时内存保留仍有成本。

真实桌面工具另验证了连续两次拖动上边框、最大化、还原及点击关闭。记录帧为 194（初始）、196／197（缩小）、198（最大化）、199（还原），进程正常退出且 stderr 为空。图像保存在 Desktop 工具记录中，不宣称存在本地 PNG。

## 独立原生验证

通过公开 C ABI 分别加载旧、新的原生 DLL，每个样本预热 16 次后执行 1000 次交替缩放，两个尺寸场景各三次，共 12,000 次操作。所有 12 个样本的最终尺寸和读回 BGRA 字节完全一致。

| 尺寸轨迹 | 旧版容量变化／1000 次 | 新版容量变化／1000 次 | 旧版耗时中位数 µs／次 | 新版耗时中位数 µs／次 |
| --- | ---: | ---: | ---: | ---: |
| 800×600 ↔ 980×708 | 1000 | 0 | 401.212 | 1.837 |
| 1920×1080 ↔ 1936×1096 | 1000 | 0 | 1375.846 | 0.436 |

该基准只衡量原生 Resize，不包含布局、重绘、GDI 提交和输入分发，不能外推为整个应用同等加速。线程周期计数也保存在原始记录中，以避免把计时量化得到的 0 ms 解释为零 CPU。

功能回归执行 7086 项，全部通过、0 跳过；该运行排除两个既有性能基准类。新增测试覆盖像素复用、失败帧、绘制中再次失效、等待更新时不压缩、监听失败重试、捕获与 HWND 更换、全部移动事件和最终位置。原生测试覆盖容量内零重新分配、嵌套图层复用、精确像素、失败回滚和空闲释放。

独立模板性能基准 1/1 通过。最终应用完成两轮控件、图像、特效、主题切换、缩放和清空，成功标记为 `generations=2 blanks=2 themes=2 resizes=2 finalBackend=Software`，21 个正式响应样本无失败。返回空窗的工作集最大为 46.941 MiB。另一次新进程 800×600 空窗检查工作集最大 21.910 MiB；因此原先严格低于 20,000,000 字节的目标仍未达标。

## 复现

在仓库根目录，按 `docs/empty-window-memory.md` 的原有 CMake 方式完整构建原生包。使用独立输出根发布，不覆盖已测载荷：

```powershell
$evidence = 'D:\path\to\new-evidence'
$nativeOutput = 'D:\path\to\native-bin'
dotnet publish tests/Jalium.UI.MemoryProbe/Jalium.UI.MemoryProbe.csproj `
  -c Release -r win-x64 -p:PublishProfile=LowMemory `
  "-p:JaliumBuildRoot=$evidence\build" `
  "-p:JaliumNativeOutputRoot=$nativeOutput" -o "$evidence\aot"

.\tools\measure-window-input-stress.ps1 `
  -ProbePath "$evidence\aot\Jalium.UI.MemoryProbe.exe" `
  -OutputDirectory "$evidence\stress-quiet" `
  -Cursor -EventsPerPhase 240 -EventRate 60

.\tools\measure-window-input-stress.ps1 `
  -ProbePath "$evidence\aot\Jalium.UI.MemoryProbe.exe" `
  -OutputDirectory "$evidence\stress-trace" `
  -Cursor -Trace -LifetimeDiagnostics -EventsPerPhase 240 -EventRate 60

.\tools\measure-window-drag-stress.ps1 `
  -ProbePath "$evidence\aot\Jalium.UI.MemoryProbe.exe" `
  -OutputDirectory "$evidence\modal-drag" -PhaseSeconds 15 -Trace
```

光标验证会操作本次创建的可见窗口。若窗口失去前台，驱动中止并保留失败结果，不向其他窗口发送输入。无 `-Cursor` 的消息模式仅供诊断，不能当作实际鼠标悬停的证据。

本机原始证据根：

```text
D:\Users\suppe\source\repos\Jalium.UI-memory-evidence\input-resize-20260917
```

`placed-before/after-quiet` 和 `placed-before/after-trace` 为同位置的正式配对；`native-benchmark` 保存离屏原生数据；`final-regression` 保存 TRX；`final-aot`、`final-release`、`final-debug` 为最终发布载荷。早期消息注入、失去焦点的中断以及临时时序追踪单独保留，不混入正式配对。逐事件临时日志代码已在最终发布前移除。

`modal-before-highrate`、`modal-after-highrate` 和 `modal-summary.csv` 保存真实模态拖拽／高频输入结果；`long-after-quiet` 保存更长的固定输入轨迹；`features-return`、`cold-after` 和 `performance` 保存收尾验证。较早 `modal-before`／`modal-after` 的外部驱动等待精度和结束锚点不准确，两个失败结果保留，未作为通过证据；修正后的脚本记录实际频率及最终边界。
